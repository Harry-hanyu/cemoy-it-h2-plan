1半年的工作规划

按阶段说明重点、问题、交付与优先级安排原因。

阶段 核心思路 主流程 重点做什么 解决什么问题 预期成果
前三个月
M1–M3		 提升人效 当前主流程不变 用 RPA / 半人工 / 已接通 API，把数据收集与初加工效率提上来；计算侧开始进入云数据仓库分层 数据收集工作量大；本地处理与人工核算耗时长，拖累出表 关键导出链路人效提升；已接通平台营业额等可出天结果表；费用审批等完成 ODS→DWD 集成与清洗输出
半年度
M1–M6		 系统化解决方案 关键节点去人工依赖 系统自动解决关键人工节点；管理报表与业务打通；跨境进销存与货值等供应链数据可靠性完善 关键依赖人工；财务与业务是否有效融合尚不清楚；管理报表与经营脱节风险 形成经营上「财务 + 业务」融合的管理模式；更多链路 API 自动入仓；评估/落地资金清分等平台化能力

优先级安排与原因

  1. 先保出表与人效，主流程不动 — 避免半年度改革一开始就打断财务关账与管理报表节奏。
  2. 收集用 RPA、计算用云数据仓库并行 — 对应「18 号出表」的两大根因，缺一不可。
  3. 费用归属等先制度 + 人工严控，平台化半年评估 — 改造审批流前先保证填报与审核准确性，再决定自研/外采清分平台。
  4. 跨境进销存、全平台营业额、货值供应链放半年度 — 依赖主数据与多方协同，适合系统化阶段交付。
尚未明确（不写入阶段表）：规划起止具体月份/财年标签；各月更细排期；前三月可量化人效 KPI（节省人天、出表日提前天数等）。见文末待补充。

2财务自动化的落地方案

结合财务实际问题：数据源、处理与核算、与现流程衔接、结果校验；并判断 18→10 号路径。

2.1 目标与根因

效率目标

月度利润 / 管理报表：现状约 每月 18 号 出具 → 逐步提前到 每月 10 号。

财务需先提供的清单

「无法在每月 10 号前提交、从而影响关账的事项清单」——协调数据方提前给数；实在给不出则用预估数据先出一份。

#根因主要表现技术方案
1 数据收集工作量大 多账户 / 多系统人工拉取 RPA
2 数据计算处理成管理报表难 大量本地处理；人工核算；二次清洗；复杂规则（科学分摊、加权成本、费用归因）；口径统一与业务流程规范；OA 等系统完善；人工预估 → 系统自动预估；资金流水与业务对账等 云数据仓库（企业云数仓 / 数据分层）

2.2 公共底座（各导出线共用）

采集（RPA / API / 半人工） → 云数据集 / 云仓 ODS（允许重复） → 清洗去重 DWD + DIM → DWS / 天结果表 / 管理报表
  • 明细层增加品牌、币种等后续计算必要维度。
  • 建立管理报表所需公共维度表（DIM）：通过金蝶 API、钉钉 API、聚水潭 API、领猫 API 定时集成至云仓，按管理口径自动计算。
  • 无更好 API 时：本地机房台式机安装 RPA，将人工步骤改为定时自动执行，结果自动入云数据集（如资金账单：每天凌晨，允许重复）。

2.3 数据导出类子方案

子项前三个月半年度
资金账单
（200+ 账户人工拉取）		 评估出纳实际操作步骤；若无更好 API → 机房台式机 + RPA 定时 → 云数据集；Python 合并清洗：ODS→DWD，挂 DIM 与公共 DIM / 清分等能力深化（细节待预算与选型补充后展开）
费用审批单 钉钉 API 集成清洗输出 ODS→DWD；改造审批流前：业务人工准确选择归属等信息，财务严格审核；解决费用归属问题 评估是否采用自研 + 外采资金清分平台（自动生成凭证、资金清分）
销售 + 库存 半人工提效：RPA + API + 企业云数仓 跨境进销存数据打通；跨境平台 API 定时入仓；ODS→DWD→DWS 输出天表
店铺账单 RPA 提效 API 自动进入企业云数仓
资金结余 评估是否需要自动化；不影响报表产出则仍按现有人工方式（口述「泗洪人工」，含义待确认） 评估是否外采资金清分平台

2.4 月度报表类子方案

子项前三个月半年度
营业额 已接通平台：经数据中台做成天结果表 打通所有平台销售额数据，系统化输出天结果表
预估报表 评估当前预估规则科学性 → 与财务确认后 → 大数据计算定时输出预估结果表
费用 / 资金核对 提升效率 自研系统 + 完善现有钉钉 OA + 规范制度

2.5 与现有财务流程衔接 & 结果准确性

  • 衔接：前三月不改主流程；数据侧提速后仍按财务既有关账与出表节奏对接；阻塞项用「提前给数 / 预估出表」机制兜底。
  • 验准（已明确的手段）：费用归属阶段靠业务准确选择 + 财务严格审核；预估规则需与财务确认科学性后再系统化；云仓侧 ODS→DWD 清洗去重。更细的对账抽样、实数回冲规则等尚未告知，不自行假设。

2.6 「18 号 → 10 号」可行性判断（基于已给信息）

判断：目标有实现路径，但是条件型可行——取决于阻塞清单与预估机制能否落地，以及收集/计算两侧提速是否到位。本文不编造提前天数承诺。

  • 路径：RPA/API 压缩收集日历天数 + 云仓固化计算压缩本地加工 + 预估子方案支持 10 号前先出表 + 费用归属/口径规范减少返工。
  • 主要前提（已口述）：财务提供 10 号前关账阻塞清单；给不出的数据允许预估；前三月主流程可维持；运营协助 API/系统盘点无覆盖缺口或有获取方案。
  • 尚缺前提（未告知）：阻塞清单正文、预估与实数切换规则、出表日分阶段里程碑、关键供应商/平台数据最晚可达日。见文末。

3技术方案和现有 IT 资产的处理

原则：暂不建设完整大型数据平台，但结构要可扩展、可维护。

3.1 已确认的技术取向

  • 采集：RPA（机房台式机）+ 开放平台 / 业务系统 API + 过渡期半人工。
  • 存储与计算：企业云数仓 / 数据中台分层（ODS → DWD → DWS / 天结果表）。
  • 对外报告云资源表述：阿里云 ECS 服务器、大数据计算引擎、RDS 数据库及配套云服务（报告不出现内部采购产品商品名）。
  • 展示层：优先核实现有帆软 BI 合同；若公司未购买或不可用，再按月采购 BI（可选 Quick BI）。
  • 半年可选平台化：资金清分平台（自研 + 外采评估）、跨境平台 API、自研核对能力与钉钉 OA 完善。

3.2 资产盘点机制（已定协作，清单正文未齐）

协作方产出目的
运营 《开放平台 API 清单》；《业务在用系统账号密码 / 管理员清单》 盘点 IT 已掌握 API/系统是否覆盖财务报表与公司经营支撑；缺口则制定获取方案。现状：电商平台 API 密钥/账号密码部分由运营管理。
财务 10 号前关账阻塞事项清单 识别业务对接滞后项，推动提前给数或预估出表。

5.2 BI：基础方案 vs 可选方案（Quick BI 刊例，中国站）

依据阿里云官方计费文档刊例；活动价以购买页为准。做报表与看报表均占用用户数。

方案规格月费量级半年占位利弊
基础建议（若需新购 BI） 高级版 10 用户 约 750 元/月 约 4,500 元 适合 IT+财务+少数业务看数；半年度过渡够用。协同用户有限。
可选扩展 高级版 20 用户 约 1,500 元/月（年费÷12） 约 9,000 元 经营融合后更多业务方可看报表；费用翻倍。
